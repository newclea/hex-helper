# GameBuddy Windows Overlay 修订与语音陪伴设计

日期：2026-09-21
需求提出人：恒祥

## 1. 背景与目标

本规格是现有《GameBuddy 交互、动态形象与气泡排版设计》的 Windows 实机反馈修订，
同时加入已经确认的语音播报陪伴服务。

目标如下：

1. 修复多显示器和负坐标环境下拖动跳边、错误上限的问题。
2. 根据猫咪所在屏幕的实际工作区动态摆放气泡，且重排时猫咪不移动。
3. 让气泡按内容自适应宽度，最大有效文本宽度为当前的两倍，并移除分页式压缩。
4. 按五张参考图重制动画，删除错误的 Codex 宠物图像。
5. 为当前气泡和后续陪伴推送提供可插拔、可关闭的 Windows 本地语音播报。

本规格只修改 Overlay 展示、动画素材、语音适配及其配置，不改变 OCR 识别、推荐算法、
LCU、Live Client 或 C++ 视觉引擎的业务判断。

## 2. 已确认的产品行为

### 2.1 拖动

- 仅在猫咪实际图像范围内按住左键 500ms 后进入拖动。
- 500ms 内松开仍执行原有短点击或重试链路。
- 猫咪可在主屏、副屏以及位于主屏左侧或上方的屏幕之间连续拖动。
- 边界来自当前电脑和当前显示器的实际工作区，不使用固定分辨率。
- 拖动位置只保存在本次进程内，重启后恢复默认位置。

### 2.2 气泡

- 气泡按内容测量结果自适应宽度，最大有效文本宽度由当前约 390px 扩大到约 780px。
- 短文本未达到换行长度时，气泡缩短到刚好容纳文本和现有控件的宽度。
- 短气泡不保留多余空白。
- 稍长文本正常换行，并继续避免末行只剩 1～2 个字。
- 不缩小字体，不改写为摘要，不分页，不滚动，也不使用窄屏堆叠布局。
- 目标电脑不会使用无法容纳该布局的极小显示器，不为这种场景增加额外分支。
- 推荐类内容保持“标题普通字重、内容粗体”。

### 2.3 气泡方向

- 猫咪靠近上边界时，气泡在猫咪下方。
- 猫咪靠近下边界时，气泡在猫咪上方。
- 猫咪靠近左边界时，气泡在猫咪右侧。
- 猫咪靠近右边界时，气泡在猫咪左侧。
- 四个角分别使用斜对角方向，例如右上角使用左下方。
- 猫咪不靠边时，选择能完整容纳气泡且可用空间最大的方向。
- 文本换行、内容更新和窗口重排都不得改变猫咪的屏幕坐标。

### 2.4 动态形象

五张用户参考图只作为视觉资料，状态映射如下：

| 状态 | 参考图与动作 |
| --- | --- |
| 等待、选英雄 | 图 1 的歪头姿态，约每 3 秒自然眨眼一次 |
| 应用刚启动 | 图 2，去姓名，约 3 秒挥手一轮并眨眼；头和身体稳定 |
| 推荐结果 | 图 3 的指向姿态，并约每 3 秒眨眼一次 |
| 未识别、失败 | 图 4 的失败姿态，并约每 3 秒眨眼一次 |
| OCR 识别中 | 图 5，循环轻微抓头，并约每 3 秒眨眼一次 |
| 长按拖动 | 复用图 5，拖动期间继续轻微抓头，不冻结动画 |

全部状态必须使用同一只猫的皇冠、耳朵、眼睛、项圈、轮廓和配色。
现有包含 Codex 小宠物的帧必须删除，不得作为回退素材。
缺失非关键动画帧时，可以回退到正确的 GameBuddy 静态猫图，但不能阻止程序启动。

### 2.5 右键菜单

右键仅在猫咪图像范围内生效。菜单按当前状态显示两项：

1. 语音开启时显示“关闭语音”，关闭时显示“开启语音”。
2. “退出”。

不显示退出确认框。菜单位置靠近点击点，并限制在点击点所在显示器的实际工作区内。

## 3. 窗口和坐标设计

### 3.1 坐标来源

猫咪在虚拟桌面中的绝对矩形是唯一位置真相。
该矩形允许负的 `left` 和 `top`，以支持位于主屏左侧或上方的显示器。
Tk 根窗口坐标只作为渲染结果，不再反向决定猫咪位置。

拖动时按以下顺序计算：

1. 根据按下点、当前鼠标点和拖动偏移计算候选猫咪矩形。
2. 使用候选猫咪中心点调用 `MonitorFromPoint` 选择目标显示器。
3. 使用 `GetMonitorInfoW` 读取目标显示器的 `rcWork`。
4. 只把猫咪矩形限制到 `rcWork` 内，得到最终猫咪绝对坐标。
5. 根据最终坐标计算气泡方向、组合窗口边界和画布内偏移。

不能根据鼠标刚进入某块屏幕就切换边界，否则猫咪尚未跨屏时会发生吸附或跳跃。

### 3.2 原生窗口移动

Windows 下使用 `SetWindowPos` 写入组合窗口的绝对虚拟桌面坐标。
Tk `geometry` 只负责请求画布尺寸，不得用带负号的位置字符串移动窗口，
因为 Tk 会把负数解释为相对屏幕右侧或下侧的偏移。

非 Windows 测试环境保留一个纯逻辑适配层，使用注入的工作区和窗口移动函数验证行为，
但正式运行路径仍以 Win32 API 为准。

### 3.3 单窗口锚定组合

继续使用一个透明 Overlay 窗口，避免拆分窗口后引入置顶顺序、焦点、点击穿透
和关闭生命周期问题。

每次布局先固定猫咪绝对矩形，再计算气泡绝对矩形。
根窗口边界是猫咪、气泡和气泡尾巴的并集。
猫咪和气泡在画布中的坐标由各自绝对坐标减去根窗口左上角得到。
这样可以调整根窗口尺寸和位置，同时保持猫咪在屏幕上的位置不变。

## 4. 气泡布局设计

### 4.1 方向选择

布局器输入猫咪矩形、气泡尺寸和当前显示器工作区，输出方向、气泡矩形和尾巴方向。

先根据猫咪与四条工作区边界的距离判断靠边状态。
两个方向同时靠边时组合成斜对角方向。
不靠边时计算上、下、左、右四个候选矩形，优先选择完整落入工作区的候选。
多个候选都可用时，选择剩余空间最大的候选。

### 4.2 文本和高度

布局器先测量每个自然段、结构化文本行和现有控件的所需宽度。
实际有效文本宽度取“内容和控件所需宽度”与约 780px 上限中的较小值。
只有内容所需宽度超过该上限时才换行，再由行数、按钮和间距计算实际高度。
原有标点保护和末行孤字平衡继续生效。
推荐结果保留完整内容，不通过分页或截断隐藏信息。

玩法按钮按现有交互展示；只有气泡文本分页相关按钮和页码被移除。
其他原有操作区域不改变语义。

### 4.3 位置稳定性

气泡内容变化时重新计算气泡矩形和根窗口并集，但猫咪绝对矩形保持不变。
拖动时以猫咪位置为输入逐帧重排；鼠标释放后保留最后的猫咪坐标。
窗口尺寸变化不能反向写入拖动状态。

## 5. 动画设计

### 5.1 逻辑状态和素材复用

保留现有业务状态映射，但允许多个逻辑状态引用同一套基础姿态：

- `idle` 和 `listening` 使用图 1。
- `greeting` 使用图 2。
- `success` 使用图 3。
- `failure` 使用图 4。
- `thinking` 和拖动覆盖状态使用图 5。

拖动是高于业务动画的临时视觉覆盖状态。
进入拖动后切到图 5 动画，释放或捕获丢失后立即恢复当前业务状态对应的动画，
不暂停或冻结时间轴。

### 5.2 帧生成

优先从参考图制作透明背景的基础帧，
再通过局部位移、轻微拉伸、压缩和旋转生成过渡帧。
眨眼只改变眼部；挥手只改变抬起的爪子；抓头只改变爪子和允许的局部轮廓。
生成补帧时不得改变角色身份特征，也不得加入参考图中不存在的宠物、文字或装饰。

每个循环约 3 秒包含一次完整眨眼。
动作状态可在眨眼之间播放局部动作，但不能通过整体抖动模拟动画。

## 6. 语音陪伴架构

### 6.1 范围

首版完整接入本地气泡摘要和当前业务事件，
同时为以后服务端推送的陪伴消息预留适配器接口。
首版不连接远端推送服务，不改变现有网络访问，不引入云端 TTS。

播报内容包括：

- 当前气泡的口语化摘要。
- 推荐结果、识别失败等需要用户注意的本地事件。
- OCR 持续超过 2 秒时的一次识别进度提示。
- 以后通过同一消息模型进入的陪伴推送。

不逐字朗读很长的气泡，不朗读按钮、页码或调试信息。

### 6.2 统一消息模型

本地事件和未来远端事件统一转换为 `SpeechMessage`，至少包含：

- `message_id`：单条消息标识。
- `source`：`local` 或预留的 `remote`。
- `kind`：推荐、错误、进度、陪伴等业务类型。
- `summary`：实际送入 TTS 的口语化文本。
- `priority`：高、普通、低。
- `dedupe_key`：去重键。
- `created_at` 和 `expires_at`：创建和过期时间。

Overlay 和业务控制器只产生消息，不直接调用 PowerShell。
语音调度器负责去重、过期、优先级和播放控制。

### 6.3 Windows TTS 适配器

首版使用一个持久 PowerShell 子进程加载 `.NET System.Speech`。
Python 通过标准输入向工作进程发送消息，避免每条播报都启动一次 PowerShell。
适配器提供 `start`、`speak`、`cancel` 和 `close`，
其余模块只依赖该接口。

语音选择顺序：

1. `overlay.json` 中显式配置的语音名称。
2. 已安装的中文女性语音。
3. Windows 默认语音。

TTS 初始化失败、指定语音不存在或工作进程异常退出时记录日志并静默降级，
不能影响 Overlay、OCR 或推荐。

### 6.4 队列和打断

- 高优先级的关键错误或推荐可以打断正在播放的低优先级陪伴语音。
- 相同 `dedupe_key` 的重复消息在有效期内只保留一次。
- 到达 `expires_at` 的消息直接丢弃。
- 低优先级陪伴消息之间至少间隔 60 秒。
- OCR 进度只有在识别持续超过 2 秒时产生一次，识别提前完成则不产生。
- 普通消息不因新的普通消息而反复打断，避免连续播报造成噪声。

### 6.5 开关和持久化

语音默认开启。`overlay.json` 保存 `voice_enabled` 和可选的 `voice_name`，只修改语音相关字段，
不改变其他配置语义。

用户选择“关闭语音”时立即停止当前播放、暂停调度并清空低优先级队列。
关闭期间新消息不入队。
队列中已有的普通或高优先级消息继续按过期时间失效，
重新开启后只允许仍有效的消息播放。

关闭应用时先停止语音调度，再取消当前播报并关闭 PowerShell 工作进程，不遗留后台进程。

## 7. 模块边界

在现有模块基础上增加或调整以下职责：

- `overlay_interaction.py`：纯坐标、显示器选择、猫咪边界限制和气泡方向算法。
- `cat_overlay.py`：Tk/Win32 适配、绝对锚点、组合窗口绘制、右键菜单和事件接线。
- `rich_text_layout.py`：内容自适应、双倍最大有效宽度下的完整内容换行，不再负责分页。
- `cat_animation.py`：新素材清单、眨眼周期、拖动覆盖和状态恢复。
- 新增语音消息与调度模块：统一消息、优先级、去重、过期和 60 秒节流。
- 新增 Windows TTS 适配模块和 PowerShell 工作脚本。
- 控制器仅把现有展示状态转换为口语化摘要，不改变推荐和识别结果。

任何新增或修改的方法不超过 80 行，单行不超过 120 个字符。
不做需求范围外的重命名、格式化或重构。

## 8. 错误处理

- Win32 显示器查询失败：保留最后一次有效工作区；
  没有历史值时使用 Tk 报告的当前屏幕范围。
- 原生移动失败：记录目标坐标和系统错误，不把失败坐标写回猫咪锚点。
- 气泡布局失败：保留上一份有效布局和完整文本，不移动猫咪。
- 动画资源失败：回退正确的 GameBuddy 静态猫图，不回退到错误帧。
- TTS 失败：停止本轮语音并静默降级，UI 和业务链路继续运行。
- 配置字段缺失或损坏：语音按默认开启处理，其他现有配置沿用原有兼容逻辑。

## 9. 自动化验证

### 9.1 坐标和布局

1. 主屏、左侧负坐标屏、上方负坐标屏和不同分辨率屏之间连续拖动。
2. 按候选猫咪中心点选择显示器，不按鼠标点提前切屏。
3. 猫咪在四边和四角时的八种气泡方向。
4. 气泡内容变长、变短或换行后猫咪绝对坐标不变。
5. `SetWindowPos` 接收负绝对坐标，Tk 只接收尺寸。
6. 右键菜单在每块屏幕的工作区内显示。
7. 短文本气泡按内容收缩；长文本在约 780px 最大有效宽度下换行，
   并保留全部字符、字重和孤字平衡。

### 9.2 动画

1. 五套参考姿态与六类使用场景的映射。
2. 所有循环约每 3 秒完成一次眨眼。
3. 启动挥手只移动抬起的爪子。
4. OCR 和拖动复用抓头素材，拖动期间动画不冻结。
5. 释放或捕获丢失后恢复当前业务动画。
6. 清单或帧缺失时回退正确静态图。

### 9.3 语音

1. 本地事件转换为口语化 `SpeechMessage`，不逐字朗读长气泡。
2. 重复、过期、优先级打断和 60 秒低优先级间隔。
3. OCR 在 2 秒前完成时不播报，超过 2 秒时只播报一次进度。
4. 指定语音、中文女性语音和系统默认语音的回退顺序。
5. 开关持久化、动态菜单文字、关闭时取消和低优先级清队列。
6. PowerShell 启动失败、异常退出和应用关闭时不阻塞主程序或遗留进程。

## 10. Windows 人工验收

1. 在至少两块位置不同的显示器之间拖动，
   猫咪不跳到屏幕另一侧，也没有固定分辨率上限。
2. 猫咪在四边和四角时气泡出现在相反方向，内容不被压成分页。
3. 拖动或气泡内容变化时猫咪自身位置不漂移。
4. 短文本气泡按内容收缩；长文本最多使用约为旧版两倍的有效宽度，
   自然换行并完整显示文本。
5. 五种视觉参考全部正确，不再出现 Codex 宠物或姓名文字。
6. 所有状态约每 3 秒眨眼；启动挥手、推荐指向、失败和抓头动作符合参考。
7. OCR 和长按拖动均显示抓头，拖动时动作持续。
8. 右键菜单显示动态语音开关和“退出”。
9. 关闭语音立即停止当前播报，重启应用后仍保持用户选择。
10. 推荐、错误、长 OCR 和低频陪伴消息按约定播报，重复内容不会连续朗读。
11. 退出应用后没有遗留 PowerShell 语音进程。

Windows 实机验收完成前，交付状态只能表述为
“代码和自动化验证完成，Windows 实机待验收”。

## 11. 完成标准

- 本规格列出的自动化测试通过，并完成 Windows 实机人工验收。
- `一键启动小猫.cmd` 仍能启动精简包，README 明确说明其他支持的启动方式。
- Overlay、OCR、推荐和关闭流程在语音不可用时仍可独立正常运行。
- 两个 Git 远端指向同一份经过验收的提交。
- 除本规格列出的窗口、布局、动画、语音、配置、文档和聚焦测试外，不修改其他链路。
